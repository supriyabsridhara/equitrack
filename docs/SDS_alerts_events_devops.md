## 2. Event-driven notification design

**Pattern.** Synchronous publish/subscribe inside the application. The system does not receive a market stream: an event is
generated by the application after it fetches a new price (user refresh or the "Refresh all" button).

| Class | Purpose |
|---|---|
| `PriceEvent` (base dataclass) | symbol, current/previous price, time, source, alert id, user id |
| `StockPriceIncreasedEvent` | price rose to or above an `ABOVE` target (`target_price`) |
| `PriceFallsBelowThresholdEvent` | price fell to or below a `BELOW` threshold (`threshold_price`) |
| `EventDispatcher` | `subscribe`, `unsubscribe`, `publish`; handlers are isolated; `strict=True` re-raises after all handlers ran |
| `NotificationService.handle_event` | the subscriber; stores one notification per event |
| `AlertService` | validates rules, evaluates alerts, publishes events |

**Rules.** `ABOVE`: `price >= target`. `BELOW`: `price <= target` (inclusive). Invalid prices (None, <= 0, NaN) are ignored.

**Duplicate prevention.** `AlertRepository.claim_trigger` performs one atomic `find_one_and_update` with filter
`{_id, is_triggered: false}`. Only the caller that flips the flag publishes the event, so concurrent refreshes and
repeated refreshes produce exactly one notification. An alert is re-armed only by **Reset** or by **editing** its
condition/target.

**Failure handling.** If creating the notification fails, the claim is released and the alert stays armed so the
next refresh retries; the price refresh itself is never broken (`notify_price_update` never raises).

**Why this design.** The service depends on repository interfaces (Repository pattern) and publishes events instead of
calling the notification code directly, so new reactions (e-mail, SMS) can subscribe without changing alert logic.

## 3. Alert API

| Method | Endpoint | Notes |
|---|---|---|
| GET | `/api/alerts[?symbol=&status=active\|triggered]` | `{"alerts":[...]}` each with `status` |
| POST | `/api/alerts` | `{stock_symbol, condition, target_price}` -> 201; 400 on invalid input |
| PUT | `/api/alerts/<id>` | change condition/target; re-arms |
| POST | `/api/alerts/<id>/reset` | re-arm without editing |
| DELETE | `/api/alerts/<id>` | |
| GET | `/api/notifications[?unread=true]` | `{"notifications":[...],"unread_count":n}` |
| POST | `/api/notifications/<id>/read`, `/api/notifications/read-all` | |
| GET | `/health`, `/ready` | liveness; readiness (MongoDB ping) |

Validation: symbol `^[A-Z0-9.\-^=]{1,15}$` (upper-cased); condition in {ABOVE, BELOW}; target a finite number > 0 (booleans rejected).

## 4. Frontend design

Single-page app (vanilla JS, Bootstrap 5 for forms/tables/modal) served by Flask. Pages: Dashboard, Find stocks,
Watchlist, Portfolio, Transactions, Alerts, Notifications. The UI only uses the REST API (contract in
`MEMBER1_INTEGRATION.md`). Unread notifications are polled every 20 seconds (toast + badge). Each alert shows a
*distance-to-trigger* track computed from the latest known price. Keyboard focus, skip link, reduced-motion and
responsive layout are supported.

## 5. DevOps design

* **Docker:** `python:3.12-slim`, non-root user, Gunicorn, healthcheck on `/health`; no secrets in the image.
* **Compose:** `web` + `mongo` with a named volume (`mongo_data`) for persistence (NFR-11).
* **Jenkins:** Checkout -> Install -> Lint (flake8) -> Test (pytest, JUnit report) -> Build image (`equitrack:<BUILD_NUMBER>`)
  -> Deploy (main only): create Secret from Jenkins credential `alpha-vantage-key`, `minikube image load`,
  `kubectl apply -f k8s/`, `kubectl set image` to the freshly built tag, `kubectl rollout status`.
* **Kubernetes:** `equitrack-app` Deployment (probes, ConfigMap + Secret env), NodePort Service 30080, `mongo` Deployment
  (strategy `Recreate`) with PVC `mongo-pvc`, ClusterIP Service `mongo`.
